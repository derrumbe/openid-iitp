IITP and WISE: where two draft profiles collide

Both drafts extend the Shared Signals Framework into non-human territory, and both arrived within three weeks of each other. They are not duplicates — but they are not cleanly separable either. Seven event pairs describe the same facts, and the two drafts disagree about who is allowed to assert them.

The seven collisions

Three of these are near-homographs — the same event under the same name, differing only by tense. The other four describe one fact from two directions.

IITP WISE Kind How they differ
workload-compromise workload-compromised Same name IITP’s is far richer — compromise_type, trust_status, a workload object carrying spiffe_id, plus affected_component and indicators. WISE’s carries only detection_method. Note IITP reaches for a SPIFFE ID here, which is WISE’s native identifier.
anomalous-workload-behavior anomalous-behavior-detected Same name Both are deliberately the low-confidence tier below the compromise event, and both say so in almost identical words. Functionally interchangeable.
trust-anchor-change trust-anchor-changed Same name WISE is substantially deeper: x509_ca vs jwks, five change types, effective_at, old_material_expiry for grace periods, and URIs to fetch the new bundle. IITP has four fields and no rotation semantics.
secret-exposure credential-compromise Same fact Both cover non-human credential exposure. IITP frames it as a leak discovered in the environment; WISE as a statement by the credential’s issuer, sitting in a lifecycle alongside credential-revoked.
federation-trust-compromise trust-domain-federation-revoked Opposed framing The clearest illustration of the split. IITP reports a detection — Golden SAML, a stolen signing key. WISE reports a decision: federation is revoked and credentials “MUST be rejected.” Same event, one observed, one declared.
critical-vulnerability-exposed workload-vulnerability-status-changed Same fact WISE follows the VEX model, so it is bidirectional — it can also say not_affected or fixed and relax a prior warning. IITP only raises the alarm; nothing lowers it.
workload-compromise supply-chain workload-provenance-changed Partial IITP folds supply-chain poisoning into one compromise event with an affected_component. WISE separates provenance as its own signal with SBOM and attestation URIs, so it can report a provenance change that is not yet a compromise.

The difference that isn’t about events

Counting events understates the split. The two drafts disagree about what a Shared Signals transmitter is — and that disagreement decides what a receiver is allowed to do on arrival.

Authority is the real fault line

WISE events are assertions by the party with standing to make them: a trust domain authority speaking about credentials it issued. IITP events are detections by a party with no standing at all — the draft says plainly that a receiver “MUST NOT treat these as commands,” and that the receiver is responsible for avoiding self-inflicted denial of service. Two events with the same name and the same payload mean different things depending on which profile emitted them.

Only IITP carries confidence

Because IITP transmitters are fallible detectors, every event may carry severity, confidence, and recommended_actions, and receivers are told to weight automated enforcement by them. WISE has severity on exactly two events and no notion of confidence — consistent with a profile where the transmitter is authoritative and simply correct.

They disagree on what a workload is called

WISE identifies subjects with wimse:// or spiffe:// URIs rooted in a trust domain. IITP invents an environment subject format and reaches for complex when it needs a workload — then puts spiffe_id inside the event payload rather than the subject. For the same compromised container, the two profiles disagree about the subject, which is the one field a receiver routes on.

Both leave the clearing story half-built

IITP has a consistent follow-up pattern — reverted, resolved, restored — but only for its three specified events. WISE only reverses on vulnerability status, via VEX. Neither can currently retract a compromise assertion, which matters most for exactly the events that overlap.

What this suggests for the way forward

The two drafts are not competing for the same territory overall. Across 27 distinct facts between them, 20 are uncontested — roughly three quarters. IITP owns the cloud control plane and tenant-level campaigns; WISE owns the credential and workload lifecycle. Neither could absorb the other without becoming something it isn’t.

The seven collisions are concentrated and tractable. Three are the same event under a different tense, and in each case one draft is clearly further along: WISE on trust anchors and vulnerability status, IITP on workload compromise. The obvious move is to assign each contested event to whichever profile already models it better, and have the other reference it rather than restate it — the pattern IITP already uses toward CAEP and RISC, where it tells transmitters to prefer the existing event.

The authority split is the part that needs a decision rather than an edit. It is a genuine architectural disagreement about what a Shared Signals transmitter is entitled to assert, and it will surface again in any future profile written by detection vendors rather than issuing authorities.
